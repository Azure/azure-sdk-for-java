# AutoRest → TypeSpec Migration — Effort Estimate

**Scope:** `azure-storage-blob`, `azure-storage-file-share`, `azure-storage-file-datalake`, `azure-storage-queue`
**Author:** Storage Java SDK team
**Status:** Draft estimate
**Baseline data:** measured from the repo on branch `feature/storage/typespec` (queue pilot already started)

---

## 1. Executive summary

The four Storage data-plane libraries are currently generated by **AutoRest** from Swagger, with Java-specific shaping done through directives in each package's `swagger/README.md` plus a hand-written `*Customization.java` post-processor. Migrating to **TypeSpec** moves all of that shaping into the spec repo (`azure-rest-api-specs`) via `client.tsp` decorators (`@@clientName`, `@@access`, `@@usage`, …) and the `typespec-java` emitter config in `tspconfig.yaml`.

The upstream TypeSpec specs **already exist** for all four packages, but **none of them carry any Java customization yet** (Blob/Files/DataLake have `0` Java directives in `client.tsp`; Queue has `1`). Every Java rename, model-split, and access rule that AutoRest does today must be re-authored in TypeSpec. The raw emitter output therefore looks very different from the shipped API (immutable models, spec-native names like `SentMessage`/`AccessPolicy` instead of `SendMessageResult`/`QueueAccessPolicy`).

**The generation mechanics are easy. The cost and risk are concentrated in preserving the existing public API (binary/source compatibility) across hundreds of generated public model classes.**

- All four upstream TypeSpec specs exist; **no Java flavor work has been done in any of them** — this is greenfield rename authoring.

## 3. Work breakdown (per package)

Each package follows the same 7-phase shape. Effort scales with the drivers in §2.

### Phase 1 — Spec sync & tooling setup
Install `tsp-client`, author/fix `tsp-location.yaml`, point at the correct `data-plane/<Service>` TypeSpec directory, run `tsp-client sync`/`generate`.
- **Effort:** ~0.5 day per package (largely solved for Queue).
- **Gotcha already hit:** the legacy `Microsoft.<Service>Storage` folders hold Swagger; the TypeSpec project lives in `data-plane/<Service>Storage` (no `Microsoft.` prefix).

### Phase 2 — `client.tsp` Java renames  *(scales with directive count)*
Re-express every AutoRest directive as a `"java"`-scoped decorator: model renames (`@@clientName`), property renames, enum names, XML wire-name preservation, pageable item names.
- Much of this can be **copied from the existing `go`/`csharp`/`javascript` scopes** already in `client.tsp` and re-scoped to `"java"`.
- **Effort:** Queue 3–4 d (first-time learning), File Share 3–4 d, DataLake 1.5–2 d, Blob 5–7 d.

### Phase 3 — `tspconfig.yaml` emitter config + model access split
Set real namespace (drop the `.tsp` suffix used for side-by-side comparison), and reproduce AutoRest flags via TypeSpec equivalents:
- internal vs. public model split → `@@access` / `@@usage` (today everything lands flat in one `models/` folder),
- `enable-sync-stack`, `disable-client-builder`, `use-input-stream-for-binary`, `default-http-exception-type`, `generate-client-as-impl`.
- **Effort:** 2–3 days per package (Blob toward the high end).

### Phase 4 — Port the `*Customization.java` post-processor  *(scales with cust-class LoC)*
Re-implement whatever the customization class does (constructor visibility, XML wrappers, javadoc, accessor tweaks) either as a TypeSpec directive or as a `typespec-java` customization class.
- **Effort:** Queue 2–3 d, File Share 2–3 d, DataLake 3–4 d (218 LoC), Blob 4–6 d (288 LoC).

### Phase 5 — Public API reconciliation + compatibility  *(HIGH risk; scales with public-model count)*
Make regenerated public clients/models **binary- and source-compatible** with the shipped library; reconcile the hand-written convenience layer (`QueueClient`/`BlobClient`/…, SAS, builders, `ModelHelper`) against new generated names; run and clear `revapi`.
- The **immutable-vs-fluent model change** is the sharpest edge — AutoRest emits `@Fluent` mutable models; the `typespec-java` emitter defaults to `@Immutable` constructor-injected models. That is a source-compat break unless configured/overridden.
- **Effort:** Queue 4–5 d, File Share 5–7 d, DataLake 4–6 d, Blob 8–11 d.

### Phase 6 — Tests, recordings, samples
Update unit/integration tests that reference internal types, re-run live + playback recordings, fix serialization edge cases (Storage is XML-heavy — a common source of emitter bugs).
- **Effort:** Queue 3–4 d, File Share 4–5 d, DataLake 3–4 d, Blob 5–7 d.

### Phase 7 — Review & codegen-team iteration
PRs to the spec repo (`client.tsp`/`tspconfig`) **and** the SDK repo, plus round-trips with the Java code-generator team for emitter bugs.
- **Point of contact:** start with **Alan**; he routes to the Shanghai Java codegen team. (Per migration kickoff.)
- **Effort:** ~2–3 days per package of active time, but **calendar latency** is the bigger factor — spec-repo PRs and emitter fixes can gate progress for days.

## 4. Per-package detail

### 4.1 Queue — *pilot*
Smallest surface (10 directives, 24 public models, 115 files) and already part-started (`tsp-location.yaml` fixed, sync working, side-by-side `tsp/` output generated). Carries the **one-time TypeSpec ramp-up cost** for the team.
- **Estimate: 15–20 engineer-days (3–4 weeks).** Use it to establish the repeatable playbook.

### 4.2 File Share — ~1.8×
High directive count (30) and large public surface (73 models). No structural surprises beyond volume.
- **Estimate: 15–20 engineer-days (3–4 weeks).**

### 4.3 DataLake — ~1.6×
Fewer directives (7) but the **largest customization class (218 LoC)** and a public surface skewed toward hand-shaped models (68 public). DataLake also historically **layers on Blob** internally — verify whether its generated layer shares Blob types.
- **Estimate: 13–18 engineer-days (2.5–3.5 weeks).**

### 4.4 Blob — ~3.0× (most complex)
Largest on every axis: 44 directives, 288-LoC customization class, 122 impl + 101 public models, 329 files. **Plus dependents:** `azure-storage-blob-batch`, `-changefeed`, `-cryptography`, `-nio` consume Blob's generated types and must be re-validated after Blob regenerates.
- **Estimate: 25–35 engineer-days (5–7 weeks)**, and **do it last** so the playbook is mature and the dependent packages absorb fewer churn cycles.

## 5. Cross-cutting / shared work (not per-package)

- **`azure-storage-common`** — shared base (SAS, policies, error plumbing). No swagger of its own, but the migration of the four packages must stay compatible with it. The current build break (`azure-storage-common:12.35.0-beta.1` unresolved → 401 from the feed) is a *local dependency/versioning* issue, not codegen, and must be sorted before any package builds end-to-end. **~1–2 days.**
- **Shared emitter/version pinning** across packages, CI pipeline updates, `Update-Codegeneration` script replacement. **~2–3 days.**
- **Review overhead & cross-package consistency.** **~2–3 days.**

## 6. Key risks & assumptions

| Risk | Impact | Mitigation |
|---|---|---|
| **Binary/source-compat breaks** on regenerated public models (esp. `@Immutable` vs `@Fluent`) | High — could block shipping | Front-load `revapi`; decide model-mutability policy in the Queue pilot and lock it in `client.tsp`/emitter config |
| **`typespec-java` emitter bugs**, especially XML serialization (Storage is XML-heavy) | High | Early engagement with Alan / Shanghai codegen team; keep AutoRest output as the golden reference for diffing |
| **Spec-repo PR latency** (customizations live in `azure-rest-api-specs`) | Medium | Batch `client.tsp` changes; parallelize review with SDK-side work |
| **Blob dependents** (batch/changefeed/cryptography/nio) regress | Medium | Migrate Blob last; run dependents' test suites against the regenerated Blob |
| **Estimate assumes single engineer new to TypeSpec** | Medium | Pilot (Queue) de-risks the unknowns; later packages reuse the playbook |

**Assumptions:** one primary engineer; ~65% effective focus (meetings, review waits); upstream TypeSpec specs remain stable; codegen-team support is available for emitter fixes.

---

## 7. Recommended sequencing

1. **Queue (pilot)** → establish the playbook, resolve model-mutability & access-split policy, shake out emitter/XML bugs.
2. **File Share** → apply playbook to a large-but-standard surface.
3. **DataLake** → reuse File Share patterns; watch the Blob-layering relationship.
4. **Blob (last)** → most complex + has dependents; benefits most from a mature playbook.
